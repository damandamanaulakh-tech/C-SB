# Backend Docs Release Asset Intake

This directory is the provenance boundary for the GitHub release `backend docs` / tag `Docs`.

## Rule

Release assets are **source evidence**, not automatically canonical Sourceborn truth.

The published release is treated as immutable upstream custody. We do not delete, rename, or rewrite release assets during intake. Instead we record every asset in `MANIFEST.json`, deduplicate by SHA-256, compare release digests against files already present in the repository, classify each asset, and propose a destination.

Promotion from this intake into `raw/`, `registries/`, `machine/`, `phase2/`, `brain/`, tests, or canonical documents requires the normal Sourceborn review/R-F-R path. This preserves the repository rule that native source truth is not silently rewritten.

## Routing classes

- `sourceborn-core` — Sourceborn/URR/core specifications and backbone material.
- `asi` — ASI catalogs, workbooks, registries, node/brain/engine material.
- `parameters` — Human/AI/ASI parameter banks and tables.
- `engines` — Definition Engine, engine catalogs, orchestration material.
- `sequence` — Universal Sequence / sequence-machine source material.
- `wisdom` — wisdom and holy-book source material.
- `tests-audits` — tests, reviews, adversarial checks, scorecards, audit material.
- `visuals` — images, diagrams, SVGs and visual references.
- `operations` — deployment, Render, handoff, site-control, project/ops material.
- `research` — RH/Riemann/Mirror/One-Dot/Hollo and other research corpora that must not become core by filename alone.
- `off-project` — obvious unrelated/personal/cross-project material.
- `quarantine` — Grok-derived material and anything explicitly blocked from canonical ingestion.
- `unclassified` — requires manual review.

## Deduplication

`MANIFEST.json` stores all release asset records, but digest-equivalent assets are grouped. The first deterministic record in each SHA-256 group is the `digest_primary`; later records point at it through `duplicate_of_asset_id`.

A duplicate release filename is never a reason to delete the upstream asset. Deduplication is an ingestion concern only.

## Existing repository matches

The manifest generator hashes the checked-out repository with SHA-256 and records exact byte-for-byte matches in `repo_sha256_matches`. Assets already represented exactly in the repository should normally be treated as provenance confirmation rather than imported again.

## Generated files

- `MANIFEST.json` — complete machine-readable release inventory and routing decisions.
- `docs/RELEASE_ASSET_INGESTION_REPORT.md` — human-readable counts, duplicate groups, routing summary, and highest-priority review queues.

Both are generated by `tools/build_release_asset_manifest.py` from GitHub release metadata and the checked-out repository.
